DNS architecture and the application layer

DNS is an application-layer protocol (RFC 1034/1035). It is a distributed, hierarchical database: the root zone delegates top-level domains such as .com, which delegate individual domains to their own authoritative name servers. No single server holds every name.

Applications almost always perform a DNS lookup before opening a TCP or QUIC connection, so slow or failed DNS delays everything that follows.

Recursive vs iterative resolution

Your computer sends one recursive query with the RD (recursion desired) flag set. The recursive resolver then asks the root, TLD and authoritative servers iteratively, following referrals, and returns the final answer with the RA (recursion available) flag. DNSGuard sets RD on every query, and the attempt details show the returned header flags.

Both are anycast services: the same IP address is announced from many locations, and your packets reach whichever instance is closest in routing terms. That is one reason latency differs between networks.

A and AAAA records, IPv4 and IPv6

  • A record: a 32-bit IPv4 address, written as four decimal octets, e.g. 192.0.2.1.
  • AAAA record: a 128-bit IPv6 address (RFC 3596), written as eight hexadecimal groups, e.g. 2001:db8::1.
  • A name can have A only, AAAA only, both, or neither. A missing AAAA record is answered with NOERROR and an empty answer section, not an error.
  • CNAME: an alias. The resolver follows it and returns the target's records; DNSGuard shows the chain.

UDP, and when DNS uses TCP

Ordinary DNS queries use UDP port 53: one request datagram, one response datagram, no connection setup, so a lookup can finish in a single round trip. UDP gives no delivery guarantee, so the client applies a timeout and may retry.

If a response is too large for the UDP payload size (DNSGuard advertises 1232 bytes with EDNS0), the server sets the TC (truncated) flag and the client repeats the query over TCP port 53 (RFC 7766). DNSGuard does this automatically and marks the attempt as a TCP fallback.

Query timeout and network latency

Latency is the time between sending the query and receiving the reply, measured here with time.perf_counter(). It includes the round-trip time to the resolver plus any time the resolver spends resolving (zero if the answer is cached).

If no reply arrives within the configured timeout, the attempt is recorded as TIMEOUT. A timeout is a failure, and its duration is never used as a latency sample. The median of successful samples is used instead of the mean because one slow outlier barely moves it.

DNS caching and TTL

Every record carries a TTL (time to live) in seconds. Resolvers keep answers in cache until the TTL expires, so a repeated query is usually much faster than the first. Negative answers (NXDOMAIN, no-data) are cached too, for the time set in the zone's SOA record (RFC 2308).

In DNSGuard you can often see this: the first attempt is slower (cache miss) and later attempts are faster. The diagnostic engine points this pattern out without claiming it is the only explanation.

Resolver reliability

Reliability here means: of the queries sent, how many produced a usable answer, and how quickly. DNSGuard reports the success count and failure rate, (failed ÷ total) × 100, for each resolver over the same set of attempts, and keeps history so you can see whether results are stable over time.
